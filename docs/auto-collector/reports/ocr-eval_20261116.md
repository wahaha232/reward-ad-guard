# 自動收取 OCR 評估報告（2026-11-16）

## 背景

使用者回報：PC 版腳本（pc-collector）的正確率比 App 版高。

本次發現的直接證據：BITWALK 的 Mintegral 廣告按鈕「立即領取禮物卡」，App 版用的 ML Kit 讀成「立即領取搜物卡」「立即領取澧物卡」。因此避開清單沒有擋到，程式點了廣告兩次，都被帶到 Chrome。

| 版本 | OCR 引擎 | 語言 |
|---|---|---|
| PC 版 | Windows.Media.Ocr | zh-Hant-TW（繁體） |
| App 版 | Google ML Kit text-recognition-chinese | 「中文」模型，以簡體為主 |

## 測試方法

用手機上的 4 張真實截圖（1220×2712）分別測試三個引擎：

- g1：Mintegral 廣告畫面
- g3：同一支廣告的結束卡
- c2：AHEALTH 睡眠模式畫面
- b2：BITWALK「賺取」頁

| 引擎 | 結果 |
|---|---|
| Windows OCR（PC 版用的） | 繁體正確，但會漏讀大標題和裝飾字（例如「抓住氣球，贏得」「福利中心」都沒讀到） |
| RapidOCR 預設（PP-OCRv4 簡體） | **輸出簡體字**（暂停、赢得、领取），還會漏字（遊戲→游、步驟→步）。不適合 |
| **RapidOCR 繁體（chinese_cht，PP-OCRv6 small）** | **四張都最好**：b2 整頁全對（價格預測、變更預測、2倍獎勵、步驟歷史記錄、賺取、內容…），c2 全對，「立即領取禮物卡」正確，大標題也讀得到；只有少數藝術字錯（爪住、繽粉水乐） |
| ML Kit（App 現用） | 無法在 PC 上跑同一張圖。已知會把「禮物卡」讀成「搜物卡／澧物卡」，其他錯字等校正模式收集資料後量化 |

## 速度與大小（PC：8 核 CPU，ONNX Runtime CPU）

| 長邊縮放 | 每張時間 | 讀到的內容 |
|---|---|---|
| 960 | 約 2.8～2.9 秒 | 大字可以，小字會漏（b2 的「變更預測」「什麼是價格預測」沒讀到） |
| 1600 | 約 5.7～5.9 秒 | 小字也讀到 |

模型大小：
- 偵測 PP-OCRv6_det_small：9.9 MB
- 辨識 PP-OCRv6_rec_small：21.2 MB
- 方向分類：0.6 MB
- 合計約 32 MB；再加上 onnxruntime-android（arm64 約 8～10 MB）

手機端的速度預估是 PC 的 2～3 倍。ML Kit 目前每次約 0.2～2 秒。

## 結論

1. **繁體模型的準確度明顯比 ML Kit 好，也比 Windows OCR 完整。**
2. **但它太慢，不能直接取代 ML Kit。** 廣告迴圈每 2～3 秒就要讀一次畫面，看倒數、找 X，手機上跑繁體模型一次可能要 5～15 秒。
3. **建議做成混合式：**
   - 廣告畫面、等待中的畫面：繼續用 ML Kit（快）。
   - App 頁面上「決定要按哪個獎勵、要避開哪個」的那一刻：再用繁體模型讀一次確認。這一步每個獎勵只發生一次，慢一點可以接受。
   - APK 會多約 40 MB（如果之後完全拿掉 ML Kit，大約只多 20 MB）。
4. **已先完成的低成本改善（App 1.2.11）：**
   - 避開比對容許錯一個中文字，例如「澧物卡」也算命中「禮物卡」；但與獎勵詞重疊、或錯的是數字/字母時不算。
   - 錯字對照表 `assets/ocr_corrections.tsv`（搜物卡、澧物卡 → 禮物卡）。
   - 「OCR 校正模式」：收取時保存截圖和 ML Kit 讀到的文字。
   - 電腦端工具 `TOOLS/ocr_calibrate.py`：用 Windows OCR 重讀同一批截圖，列出錯字對照建議。

## 下一步

1. 手機打開「OCR 校正模式」，正常收取 1～2 天。
2. 執行 `python TOOLS/ocr_calibrate.py --serial <手機>`，產生錯字報告，量化 ML Kit 錯多少、錯在哪裡。
3. 依錯字數量決定要不要做混合式繁體 OCR。若要做：
   - 先做 onnxruntime-android 的原型，量手機上的實際速度；
   - 再決定縮放長邊（960 或 1280）和要在哪些時機呼叫。
