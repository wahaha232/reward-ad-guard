## 2. 搬到手機上的技術對應

| pc-collector（電腦） | 手機端做法 | 備註 |
|---|---|---|
| `adb exec-out screencap` | `AccessibilityService.takeScreenshot()`（Android 11+） | 不需要額外授權；系統限制每次間隔約 0.33 秒，夠用 |
| Windows OCR（`scripts/ocr.ps1`） | **Google ML Kit 中文文字辨識**（裝置端） | 內建模型約增加 APK 20 MB；或用 Play 服務版（較小，首次要下載）。Windows OCR「中文逐字加空格」的問題不存在，但要重調文字比對 |
| uiautomator dump（BitWalk 首頁會卡 idle） | **直接讀無障礙節點樹** | 最大優勢：守衛本來就讀得到 BitWalk 的「可兌換 50 個印章」等文字，不用等畫面靜止；OCR 只當備援 |
| OpenCV 模板比對（`close_circle`、`next_circle`、`back_arrow`） | Kotlin 自寫小範圍 NCC 比對（只搜四個角落），或引入 OpenCV Android | 只比對角落小區域，自寫即可，免掉 OpenCV 30 MB 以上的體積 |
| `adb input tap` | `dispatchGesture`（守衛已開 canPerformGestures） | 已在用 |
| `adb shell input keyevent BACK/HOME` | `performGlobalAction` | 已在用 |
| `am start` 開 App | `startActivity`（無障礙服務可從背景啟動） | ReturnController 已在用 |
| `reconnect.py` 斷線重連 | **不需要** | 在手機上跑沒有連線問題 |
| 鎖定畫面偵測 | `KeyguardManager.isKeyguardLocked()` | 手機鎖住就暫停並通知；無法替使用者解鎖 |
| 螢幕保持亮著 | 無障礙浮層（TYPE_ACCESSIBILITY_OVERLAY）設 keepScreenOn | 不需要「顯示在其他 App 上層」權限 |
| `control/PAUSE`、`STOP` 控制檔、浮動控制窗 | 常駐通知上的「暫停／繼續／結束」按鈕＋App 內控制頁 | v1.1.0 已有「暫停守衛」可延用 |
| `runlog`／events.jsonl／截圖 | 既有 Room 事件資料庫＋App 私有目錄存截圖 | 匯出功能已有 |
| `redirect.py` 跳轉偵測 | **直接用守衛的 RedirectChainPolicy／ReturnController** | 守衛這部分比 pc-collector 成熟 |
| tkinter GUI（UI.bat） | Compose 新頁籤「自動收取」 | 選 App、數量（不限或收滿 N）、開始／暫停／結束、即時狀態 |

## 3. 架構設計

```
RewardAdAccessibilityService（單一無障礙服務）
 ├─ Guard 模式（現有）：使用者自己操作時防跳轉
 └─ Collector 模式（新增）：自動收取
      CollectorEngine（協程迴圈，取代 base.py 的 collect/_collect_tabs/_handle_ad）
       ├─ ScreenReader：節點樹優先 → ML Kit OCR 備援 → 合成 Snapshot（文字框清單）
       ├─ CornerGlyphMatcher：>> / X / ← 模板比對（只搜角落）
       ├─ Actor：點擊、返回、開 App、等待（含暫停時間不計入逾時）
       ├─ AdHandler：廣告判定、找關閉／下一步、逾時處理、install card、獎勵對話框
       └─ AppProfiles：BitWalk / AHEALTH / HAHAGO / WALK EARN / LINE 散步趣 / 抽抽樂
```

**兩種模式必須互斥**，這是最重要的設計點：
- Collector 執行中，守衛的「自動點擊關閉鈕」和「跳轉自動拉回」要讓給 Collector 決定，否則兩邊會同時點擊、同時按返回（10-16 已看過守衛自己的點擊和腳本互相干擾）。
- 跳轉偵測仍由守衛的 RedirectChainPolicy 判斷，結果交給 Collector 處理（拉回後繼續等廣告結束）。
- 使用者一碰螢幕（守衛已有 TYPE_TOUCH_INTERACTION_START／點擊偵測）→ Collector 自動暫停，避免跟人搶操作。

**Snapshot 統一成「文字框清單」**：這樣 pc-collector 的 `tests/fixtures/*.ocr.json`（真實截圖的 OCR 結果，共 30 多個情境）可以直接轉成 Kotlin JVM 測試，各 App 的判斷邏輯有現成回歸測試可用。

## 4. 分階段計畫

| **2 引擎** | 移植 base.py 的狀態機：開 App→找領獎按鈕→判斷廣告→等待／關閉／下一步→確認獎勵→下一輪；暫停、結束、上限、逾時；與守衛互斥 | 用 fixtures 跑通 JVM 測試；手機上「乾跑」（只辨識不點擊）能正確說出每個畫面的判斷 |

| **5 介面與發版** | 「自動收取」頁、執行紀錄、截圖保留選項、通知；README；以雲端更新發 v2.0.0 | 使用者自己從頭跑一次完整流程 |

規模估計：pc-collector 核心約 6,700 行 Python（含 GUI），移植成 Kotlin 約 4,000～5,000 行，另加測試。

## 5. 主要風險

1. **OCR 換引擎**：ML Kit 與 Windows OCR 的斷字、框線位置不同，pc-collector 的關鍵字與座標規則要重新校正；節點樹讀得到的 App（BitWalk 是 Flutter，有 semantics）可大幅降低依賴。
2. **廣告畫面讀不到**：多數廣告 SDK 的 X／>> 是畫在 WebView 或影片上的圖示，只能靠截圖模板比對；pc-collector 已累積的「只搜角落」「避開商店連結」規則要完整搬過來（11-09、11-11 都踩過誤點導流）。
3. **手機必須亮屏解鎖**：在手機上跑時手機不能拿來做別的事；使用者一操作就暫停。
4. **HyperOS 背景限制**：長時間執行要「自啟動」＋「省電無限制」，否則服務會被殺（11-04 已證實這是「無法運作」的原因）。
5. **服務條款**：自動看廣告領獎勵可能違反各獎勵 App 的使用條款，有帳號被停權或獎勵被取消的風險，請自行評估。
6. **兩套程式並存的維護成本**：手機版穩定前，pc-collector 仍是主力；規則修正要兩邊同步，或決定 pc-collector 凍結只修 bug。
